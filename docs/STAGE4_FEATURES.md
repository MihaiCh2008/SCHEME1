# Stage 4: Features and token safety

_Built and checked 2026-10-12._

## 1. Feature engine (`scheme1.features`)

`compute_features(candles, symbol, interval, at)` returns a `FeatureSnapshot`. `snapshot_at(store, symbol, interval, at)` builds one from stored clean candles. Backtests and paper trading call the same function.

**Rules**
- **No look-ahead.** A candle is used only if it is closed and its close time is at or before `at`. `as_of` is the close time of the last candle used.
- **No computing across gaps.** Only the trailing run of consecutive candles is used. `bars_available` reports its length.
- **Fixed window.** Every feature reads at most the last `LOOKBACK = 64` candles. The same 64 candles always give the same values, however much older history was loaded.
- **`None` = not computable.** That means too few candles for that feature, or a zero denominator. A flat price gives RSI `None`, not 50. `warmup_complete` is true only with all 64 candles.
- Floats for statistics, Decimal stays the type for money (D5).

**Feature set `f1.0.0`**

| Key | Meaning | Candles needed |
| --- | --- | --- |
| `bars_available` | Length of the gap-free run used (max 64) | 1 |
| `ret_1`, `ret_3`, `ret_12` | Log return over 1/3/12 candles | n+1 |
| `vol_12`, `vol_48` | Sample std-dev of 1-candle log returns | 13 / 49 |
| `ema_ratio_9_21` | EMA9 / EMA21 − 1 (EMAs seeded with the window's first SMA) | 21 |
| `close_vs_ema_21` | Close / EMA21 − 1 | 21 |
| `rsi_14` | Wilder RSI | 15 |
| `atr_pct_14` | Wilder ATR / close | 15 |
| `volume_usd_12` | Volume summed over 12 candles (USD for GeckoTerminal) | 12 |
| `volume_ratio_12_48` | Mean volume of the last 12 / mean of the last 48 | 48 |
| `range_pos_48` | Where the close sits in the 48-candle high-low range, 0..1 | 48 |
| `drawdown_48` | Close / 48-candle high − 1 | 48 |
| `zero_volume_frac_48` | Share of the last 48 candles with no trades (illiquidity) | 48 |

**Checks.** 12 feature tests:
- Future candles, an open candle at the edge, or a wildly different future never change a snapshot.
- Older history doesn't change the values.
- Gaps reset the run.
- Zero denominators give `None`.
- The store path cites the right batch ids.
- RSI reproduces StockCharts' published Wilder example (70.53, then 66.32) to 0.01.

## 2. Token safety (`scheme1.safety`)

- `GeckoTerminalPools.snapshot()` and `DexScreenerPools.snapshot()` each return a `PoolSnapshot`: base-token mint, liquidity in USD and pool creation time. Each costs one API call. GeckoTerminal shares the ~10/min budget with candles; DexScreener is paced at 1 call per second.
- Snapshots aren't stored (D11).
- `evaluate()` returns a `SafetyReport`. The contract makes `tradable` true **only** if every check is `pass`. `unverified` blocks exactly like `fail`.

| Check | Rule | Data |
| --- | --- | --- |
| `base_token_agrees` | Both providers name the same mint for the pool | GeckoTerminal + DexScreener |
| `min_liquidity` | **Lower** of the two figures ≥ $25,000. If the figures differ by more than 1.5×, or only one provider answered → unverified | GeckoTerminal + DexScreener |
| `min_pool_age` | **Youngest** reported creation date ≥ 24 h ago (the providers disagree by months on old pools) | GeckoTerminal + DexScreener |
| `mint_authority_revoked` | Nobody can mint new supply | Solana RPC |
| `freeze_authority_revoked` | Nobody can freeze holders' tokens (the classic honeypot) | Solana RPC |
| `token_extensions_safe` | Token-2022 only: metadata extensions pass. Permanent delegate, transfer hook, transfer fee, frozen-by-default, non-transferable, pausable and confidential transfers fail. Any other extension is unverified until reviewed | Solana RPC |
| `holder_concentration` | Largest wallet ≤ 10% of supply and top 10 wallets ≤ 30% | Solana RPC |

Snapshots older than 10 minutes are ignored. The limits live in `SafetyConfig` (version `s1.1.0`).

**How holder concentration works** (`scheme1.safety.solana`):
1. `getTokenLargestAccounts` returns the 20 largest token accounts.
2. `getMultipleAccounts` returns their owners. Amounts are grouped by owner, so one wallet with several accounts counts once.
3. Each owner is classified by the Ed25519 curve test Solana itself uses. Wallet keys are on the curve. Program-derived addresses (pool vaults, bonding curves, lockers) are off it, and those are excluded and reported separately.
4. If the 20 accounts contain fewer than 10 wallets, each missing wallet is assumed as large as the smallest account seen, so the top-10 figure is an upper bound.

The curve test was checked against 500 keys generated by the `cryptography` library (all on-curve) and a known PDA (Raydium's AMM authority, off-curve). Random 32-byte values come out about 50% on-curve, as theory predicts.

Known limits:
- Tokens a team keeps in a locker or vesting program count as "program-controlled" and are excluded. That is the usual convention, but a locker that unlocks soon is a real risk the check doesn't see.
- Only the largest 20 accounts are visible through the standard RPC.

The RPC URL comes from `SCHEME1_SOLANA_RPC_URL` (default `https://api.mainnet-beta.solana.com`). Provider URLs carry API keys, so the code never puts the URL into an error or a log. Only read-only RPC methods are used: no keys, no signing, no transactions.

Command: `python -m scheme1.safety.cli --pool <pool address>`. Exit code 0 = tradable, 1 = blocked.
